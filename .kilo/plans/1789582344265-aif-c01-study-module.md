## 5. Reglas de contenido

**Agrupación:** cada Task se divide en 3–7 `GrupoTematico` según afinidad real de los objectives; cada objective debe aparecer en ≥1 grupo (validado). Ejemplo de T3.2: Fundamentos · Técnicas · Templates y calidad · Guardrails y buenas prácticas · Riesgos · Prompt Management.

**Profundidad y presupuesto** (anti-inflación, §4):

| Profundidad | Bloques | Palabras | Obligatorio |
|---|---|---|---|
| `esencial` | 1–3 | 80–200 | concepto + 1 clave o error común |
| `estandar` | 2–5 | 200–450 | concepto + 1 comparación/`cuandoUsar` + 1 ejemplo |
| `critico` | 4–8 | 400–800 | concepto profundo + 1 comparación + 1 escenario + 1 error común |

Techo blando: 2 000 palabras por Task Statement. Objetivos `critico` iniciales: 2.1 agentic AI/MCP, 2.3 Bedrock/AgentCore/Strands/Kiro/Quick, 3.1 RAG + vector DBs + prompt caching, 3.2 técnicas + riesgos + Prompt Management, 3.3 fine-tuning/RLHF, 3.4 ROUGE/BLEU/BERTScore, 4.1 responsible AI/sesgo, 5.1 prompt injection/grounding/guardrails, 5.2 governance.

**Preguntas** (guía, no meta rígida): objective `esencial` 1–2, `estandar` 2–3, `critico` 3–4. Mínimos validados: cada objective ≥1 pregunta; cada objetivo `critico` ≥1 de tipo `escenario` o `tradeoff`; banco por dominio ≥ necesidad del examen final + 2 (D1 ≥15, D2 ≥18, D3 ≥20, D4 ≥11, D5 ≥11; total ≈75). Mezcla obligatoria de tipos por dominio: ≥1 `escenario`, ≥1 `comparacion`, ≥1 `tradeoff` o `metrica`, ≥1 `servicio` o `seguridad`.

**Flashcards** (§10): solo donde aporten recuerdo recuperable. Prohibido el par definición→definición ("¿Qué es RAG?" → "Retrieval-Augmented Generation"): las tarjetas de tipo `definicion` deben formularse como escenario o consecuencia. Cada objetivo `critico` ≥1 tarjeta; no se exige tarjeta por objective (la excepción se declara en `OBJETIVOS_SIN_TARJETA`).

**Comparaciones** (§9): pares reales del blueprint, cada uno con escenario A/B y pregunta obligatoria. Mínimos: 2 en el prototipo (3.2), y en el módulo completo ≥14 (por ejemplo: fine-tuning vs RAG, embeddings vs tokens, precision vs recall, accuracy vs F1, Bedrock vs SageMaker AI, IAM vs Guardrails, CloudTrail vs CloudWatch, MCP vs API, agente vs workflow, vector DB vs knowledge base, training vs inference, clasificación vs regresión, pre-training vs fine-tuning, exposure vs poisoning).

**Precisión** (§30 y rigor): no inventar servicios ni capacidades; todo servicio citado debe existir en `serviciosEnAlcanceAifC01`; no incluir cifras de cuotas, límites ni precios de AWS (token-based pricing solo como concepto).

## 7. Progreso por evidencia y Weak Areas

`src/lib/aifC01Progress.ts`, clave `devapp:aif-c01:progress`, patrón de `src/theme/store.ts`:

```ts
type EstadoObjetivo = 'pendiente' | 'estudiado' | 'practicado' | 'dominado';
interface ProgresoAifC01V1 {
  version: 1;
  objetivos: Record<string, { estado: EstadoObjetivo; leidoEn?: string; historial: Array<{ fecha: string; correcto: boolean }>; proximoRepaso?: string }>;
  tarjetas: Record<string, { sabidas: number; falladas: number; ultimaVez: string }>;
  intentos: Array<{ id: string; tipo: 'task' | 'dominio' | 'final' | 'repaso'; scope: string; fecha: string; total: number; correctas: number; duracionMs: number; falladas: string[] }>;
  preferencias: { temporizadorFinal: boolean };
}
```

**Transiciones (heurística transparente, visible en la UI):**

- `pendiente` → `estudiado`: el usuario pulsa "Entendido" en el task (acción explícita, no auto-scroll).
- `estudiado` → `practicado`: ≥1 respuesta o ≥1 tarjeta marcada "la sabía" en ese objective.
- `practicado` → `dominado`: en las **últimas 5** respuestas del objective, ≥4 aciertos **y** la última correcta **y** ≥1 tarjeta "sabida" de ese objective.
- `dominado` → `practicado` (decaído): 2 fallos en las últimas 3 respuestas. Al alcanzar `dominado` se fija `proximoRepaso = +7 días`; si llega la fecha, el objective entra en debilidades como "repaso vencido".
- La UI muestra el porqué: "dominado · 4/5 aciertos recientes · 2 tarjetas".

**Weak Areas** (`/ai-practitioner/debiles`): prioridad (1) error ratio = `fallos/(aciertos+fallos)` con ≥2 respuestas, descendente; (2) objectives sin practicar; (3) fallos recientes (últimos 7 días); (4) objectives `critico` sin `dominado`. Se muestra `%` de dominio o de objetivo y un CTA que lanza `practica/debil` con esa selección.

**Repaso** (`/ai-practitioner/repaso`): cola mixta = preguntas falladas + tarjetas de objectives no dominados + comparaciones de esos objetivos; al terminar ofrece repetir solo los fallos y registra el intento.

## 16. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Deriva del vocabulario oficial | El `titulo` de cada objective se toma del blueprint por índice; tests de huérfanos y cobertura |
| Contenido inflado | Presupuesto por profundidad + techo por task + regla "mínimo necesario para aplicarlo" |
| Estructura que no escala | Prototipo con parada obligatoria (§11); prueba explícita con objetivos dispares (5.1) y con volumen (~600 entradas de índice) |
| Romper la app | Solo una entrada de menú y rutas; `vitest run` completo como red; ninguna vista del módulo importa auth/Firestore |
| Vistas del prototipo con datos vacíos | Estados vacíos honestos y examen final deshabilitado con motivo, nunca cifras inventadas |
| Workbox >2 MB por chunk | Verificación en `dist/sw.js`; `maximumFileSizeToCacheInBytes` si aplica |
| `vite.config.ts` con cambio local pendiente (salto de línea final) | No revertirlo; editar solo si hace falta Workbox |
| Confundir 12/16 de `simulacrosAifC01` con los 65 del final | `simulacrosAifC01` no se usa ni se muestra en el módulo |
